# Architecture

How this repository is laid out and how its parts fit together, for someone about to read or change it.

The architecture of the application it scaffolds is described in the scaffold's own
[AGENTS.md](../template/base/AGENTS.md) and in
[design/W1-STACK-SPEC.md](../design/W1-STACK-SPEC.md). Project terms used here are defined
in the [glossary](glossary.md).

## Two products in one repository

1. **The installer**, a Node CLI with no runtime dependencies ([installer/](../installer/)).
2. **The template** it installs ([template/](../template/)): the gate scripts, hooks,
   workflows and reference app that end up in a project.

Everything else, chiefly [scripts/](../scripts/), [tests/](../tests/) and
[.github/](../.github/), exists to hold those two to the standard the template imposes on a
project. This repository is called the factory in its own comments, and an installed project
the consumer.

## Where a project's files come from

The shipped docs name files by where they land in a project (`tools/check-secrets.mjs`).
In this repository they live under a template layer:

| In a project | In this repository |
|---|---|
| `tools/` (gates, registers, generators) | [template/base/tools/](../template/base/tools/), plus `tools/` under [template/stack/](../template/stack/), [template/demo/](../template/demo/) or a module |
| `.claude/` (hooks, agents, commands, rules, skills, settings) | [template/base/.claude/](../template/base/.claude/) |
| `.github/` (workflows, CODEOWNERS, pull request template) | [template/base/github/](../template/base/github/) and a module's `github/` |
| `docs/` (doctrine, gates catalog, ADRs, runbooks) | [template/base/docs/](../template/base/docs/) and a module's `docs/` |
| `apps/`, `packages/`, `supabase/` | [template/stack/](../template/stack/), with [template/demo/](../template/demo/) or a [preset](../template/presets/) laid over it when chosen |
| `tests/rls/`, `maestro/`, `specs/` | [template/base/tests/](../template/base/tests/), [template/base/maestro/](../template/base/maestro/), [template/base/specs/](../template/base/specs/) |
| `AGENTS.md`, `CLAUDE.md`, `SECURITY.md`, `LICENSE`, `CITATION.cff`, `eslint.config.mjs`, `knip.json`, `tsconfig.json`, `renovate.json`, `pnpm-workspace.yaml` | The same name under [template/base/](../template/base/) |
| `.gitignore`, `.gitattributes`, `.editorconfig`, `.nvmrc`, `.node-version`, `.gitleaks.toml`, `.dependency-cruiser.cjs`, `.mcp.json`, `.env.example` | The same name without its leading dot, under [template/base/](../template/base/) |
| `package.json` | `package.json.tmpl`, in each tree that ships one |
| `.harness/manifest.json` | No template file: `init` and `update` write it |

The installer reverses the storage conventions on the way out: it adds the dot back
(`RENAMES` in [installer/lib/layout.mjs](../installer/lib/layout.mjs)), drops `.tmpl`, and
fills in the `{{PLACEHOLDER}}` values. Template workflows are stored without the dot so they
can never run in this repository's own Actions. `.claude/` keeps its dot.

## The installer

[installer/cli.mjs](../installer/cli.mjs) dispatches to one file per command:
[init](../installer/commands/init.mjs), [update](../installer/commands/update.mjs),
[doctor](../installer/commands/doctor.mjs), [graduate](../installer/commands/graduate.mjs),
[enable](../installer/commands/enable.mjs) (which also handles `disable`),
[eject](../installer/commands/eject.mjs) and
[apply-proposal](../installer/commands/apply-proposal.mjs). The
[CLI reference](cli.md) documents every flag.

`init` renders the template into a target directory. It resolves `base` plus
`stack`, plus the modules chosen by tier or `--modules`, substitutes
`{{PLACEHOLDER}}` tokens from a closed registry
([installer/lib/placeholders.mjs](../installer/lib/placeholders.mjs)), and writes
`.harness/manifest.json`.

The manifest is what makes upgrades possible. It records:

- `harnessVersion`, the version that last wrote the install, and `baseVersion`,
  the version whose rules the project has fully adopted. The gap between them
  is how a new gate reaches an old project without breaking it on arrival (see
  Ramps below).
- The tier, the modules and the placeholder answers.
- For every installed file, a mode and a sha256.

The mode decides what `update` may do to a file:

| Mode | Meaning | On `update` |
|---|---|---|
| `owned` | Harness machinery: gate scripts, hooks, workflows, harness docs | Replaced when the file still matches its recorded sha. If the consumer changed it, their copy is kept and the incoming version is parked under `.harness/pending/`. |
| `seeded` | The consumer's code and decisions: app source, the pnpm catalog, reviewed allowlists | Never touched. `--refresh-seeded <path>` pulls a new template version on request. |
| `config` | `tools/harness.config.mjs`, the gate chain definition | Edited only through recorded `configSteps`, so a new gate can be inserted without overwriting local additions. |

`update` snapshots every path it might touch under `.harness/rollback/` before
its first write, writes atomically, and writes the manifest last, so an
interrupted update can be re-run or rolled back. `doctor` reports drift.
`graduate` advances `baseVersion` once no ramp note remains. `eject` removes the worked
example from an install made with `--with-demo`, and `apply-proposal` lets a person apply a
register edit an agent staged.

## The three enforcement layers in an installed project

The paths in this section are install paths; each links to its file in this repository.
All three layers read the same definition of the gate chain,
[`tools/harness.config.mjs`](../template/base/tools/harness.config.mjs), so they cannot
disagree about what is required.

1. **Before a tool runs.** Claude Code `PreToolUse` hooks judge every shell
   command, file write and MCP call against data tables in
   [`.claude/hooks/lib/guard-rules.mjs`](../template/base/.claude/hooks/lib/guard-rules.mjs).
   Each hook is started through
   [`launch.mjs`](../template/base/.claude/hooks/launch.mjs), which exits 2 (block) if the
   hook cannot load, so a broken hook does not fail open.
2. **Before a turn ends.** The `Stop` hook
   ([`stop-validate-gate.mjs`](../template/base/.claude/hooks/stop-validate-gate.mjs)) runs
   the validate chain and the Stop-only steps (RLS isolation, both unit suites with coverage,
   diff coverage, duplication, i18n, test quality, the mobile perf closure, reviewer
   verdicts) and sends the agent back to work when one fails.
3. **Before a merge.** The consumer's workflows run the same chain with
   `--min-floor`, against
   [`tools/validate.floor.json`](../template/base/tools/validate.floor.json), a frozen copy
   of the step list. A project can add steps to its chain. It cannot remove one without CI
   noticing, because the floor ships as an owned, hash-pinned file.
   [`tools/stop.floor.json`](../template/base/tools/stop.floor.json) does the same for the
   Stop chain.

`gate-integrity`, the second step of the chain, hashes the owned files against
the manifest. Editing a gate to make it pass turns that step red.

The local layers are tamper-evident, not tamper-proof: an agent with shell
access can get around them. CI and code-owner review are the backstop.
[SECURITY.md](../SECURITY.md) and
[security/assurance-case.md](security/assurance-case.md) state the limits.

## Ramps: how a new gate reaches an existing install

A new gate would turn every existing project red on the day it upgrades. So a
gate can ship with a ramp. For an install whose `baseVersion` is older than the
gate, its findings are printed as notes, not failures, until a named release.
After that release they are failures.
[template/migrations.json](../template/migrations.json) records each release's ramps, and
[scripts/check-ramp-ledger.mjs](../scripts/check-ramp-ledger.mjs) computes which installed
versions a release will turn red and requires the record to say so.

Ramps are for new gates. A raised security floor is not ramped, and reaches
every install at once.

| Mechanism | What it establishes |
|---|---|
| [tests/](../tests/) (`node --test`) | Tests for the installer, the gate scripts, the hooks and the factory's own checks |
| [tests/canary/injections.json](../tests/canary/injections.json) and [scripts/check-canary-coverage.mjs](../scripts/check-canary-coverage.mjs) | Every gate, every guard rule and every CI job has a registered proof that it can fail. A gate that cannot go red is treated as decoration. |
| `selftest.yml` `installer-unit` | The test suites and the factory checks pass on Linux, Windows and macOS, above coverage floors that only rise |
| `selftest.yml` `bootstrap-linux` | A scaffold rendered with no edits passes the whole chain, against a live Supabase stack, on Node 22 and 24 |
| `selftest.yml` `macos-scaffold` | The same scaffold passes on macOS without Docker; any skip but the database gate's fails it |
| `selftest.yml` `canary` | Each registered violation, injected into a real scaffold, turns the matching gate red |
| `selftest.yml` `demo-eject` | An `init --with-demo` scaffold passes the chain and the live database proofs, and after `eject` it equals a default scaffold byte for byte and passes the chain again |

windows, dated obligations, dead citations and the vulnerability scan of the

can-fail proof for each of these.

## The documentation site

[docs-site/](../docs-site/) renders the pages `init` installs under `docs/`, reading them in
place from [template/base/docs/](../template/base/docs/) and `template/modules/*/docs/`,
along with the project pages in this folder. It copies nothing, so every page has one source.
[.github/workflows/pages.yml](../.github/workflows/pages.yml) builds it on pull requests that
touch the template's docs or the site, and deploys it to GitHub Pages from `main`. A pull
request that touches only this folder does not trigger that build.

## Release path

A tag `v*` starts [release.yml](../.github/workflows/release.yml). It re-runs the gates,
waits for green `selftest.yml` and `lint.yml` runs on the tagged commit, checks that the
CHANGELOG has a section for the tag, runs `npm pack`, signs a build provenance
attestation for the tarball, and publishes a GitHub Release. Its `publish-npm`
job then publishes that same tarball to the npm registry through trusted
publishing (OIDC) and reads the registry back to confirm the bytes and the
provenance ([scripts/ci/npm-publish.mjs](../scripts/ci/npm-publish.mjs)).
[CONTRIBUTING.md](../CONTRIBUTING.md), "Releases", is the procedure.

## Reading the code

Five files show how the machinery is built:

1. [template/base/tools/lib/gate.mjs](../template/base/tools/lib/gate.mjs) is the one contract
   every gate script goes through: a missing prerequisite skips loudly on a laptop and fails
   in CI, and every failure ends with a `FIX[<gate>]:` line that reproduces it.
2. [template/base/tools/validate.mjs](../template/base/tools/validate.mjs) is the runner that
   defines "done" for both the Stop hook and CI; it refuses to run without a valid frozen
   floor, and runs read-only gates in parallel while keeping the steps that touch git apart.
3. [template/base/.claude/hooks/launch.mjs](../template/base/.claude/hooks/launch.mjs), with
   [lib/hookio.mjs](../template/base/.claude/hooks/lib/hookio.mjs), turns a hook that cannot
   load into a block instead of a silent pass, and says in its header the one case it cannot
   cover: a damaged `launch.mjs` itself.
4. [template/base/.claude/hooks/pretool-bash-guard.mjs](../template/base/.claude/hooks/pretool-bash-guard.mjs),
   with [lib/guard-rules.mjs](../template/base/.claude/hooks/lib/guard-rules.mjs) and
   [tests/hooks/hook-contract.test.mjs](../tests/hooks/hook-contract.test.mjs), is a short
   piece of plumbing over a rule table that holds only data, where every rule id has its own
   deny and allow cases.
5. [template/base/tools/check-e2e.mjs](../template/base/tools/check-e2e.mjs), with
   [tests/gates/check-e2e.test.mjs](../tests/gates/check-e2e.test.mjs), is a small gate that
   reads top to bottom, and a test that drives every branch through a stand-in `pnpm` with a
   Windows twin.

Factory checks that need to be proven red as pure functions keep their judgement in
[scripts/lib/](../scripts/lib/) and a thin runner beside it, for example
[scripts/lib/ramp-verdict.mjs](../scripts/lib/ramp-verdict.mjs) and
[scripts/ci/ramp-verdict.mjs](../scripts/ci/ramp-verdict.mjs). Comments across the
machinery are long: they say why each check exists, often with the incident behind it, and
the CHANGELOG holds the full history.
